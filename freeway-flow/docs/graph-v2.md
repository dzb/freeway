# freeway-flow 新图设计

> 目标：定义一套适合 Freeway 的 canonical graph 格式。
>
> 约束：旧图继续可读，新图只走一套字段和一套运行模型，不再依赖兼容别名。

## 1. 设计目标

新图的目标不是扩展旧格式，而是把“定义”“编译”“执行”分开。

1. 定义层只表达业务图，不表达运行态。
2. 编译层把定义转换为只读运行图。
3. 执行层只处理单次 flow 的状态流转。
4. 兼容层只负责旧图导入，不进入主设计路径。
5. v2 运行时必须同时能直接跑旧图和新图，作为迁移过渡期的统一入口。

## 2. 新图原则

### 2.1 单一字段集

新图只保留一套字段，不再提供 `layout/nodes`、`when/condition` 这类双写法。

### 2.2 显式入口

新图必须显式声明入口节点，不再依赖“第一个无前驱节点”这种推断规则。

### 2.3 边上放条件

分支条件优先挂在 `link` 上，而不是散落在节点内部。

### 2.4 运行态不回写模型

执行过程中的 `context`、`trace`、`exchanger`、停止标志，都不属于图定义。

### 2.5 编译后只读

图定义一旦编译，得到的运行图应当是只读结构，运行时不再改写节点和边本身。

## 3. 推荐模型

### 3.1 图定义

```json
{
  "id": "order-flow",
  "title": "Order Flow",
  "driver": "default",
  "version": 2,
  "entry": "start",
  "meta": {
    "biz": "order"
  },
  "nodes": [
    { "id": "start", "type": "START" },
    { "id": "validate", "type": "ACTIVITY", "task": "validateOrder" },
    { "id": "approve", "type": "ACTIVITY", "task": "approveOrder" },
    { "id": "end", "type": "END" }
  ],
  "links": [
    { "from": "start", "to": "validate" },
    { "from": "validate", "to": "approve", "when": "${ok}" },
    { "from": "approve", "to": "end" }
  ]
}
```

### 3.2 节点字段

| 字段 | 说明 |
|---|---|
| `id` | 节点唯一标识 |
| `type` | 节点类型，必须显式声明 |
| `title` | 展示名称，可选 |
| `meta` | 节点元数据，可选 |
| `task` | 节点任务标识或任务名，可选 |
| `when` | 节点级条件，仅在确实需要时使用 |

### 3.3 边字段

| 字段 | 说明 |
|---|---|
| `from` | 起点节点 id |
| `to` | 终点节点 id |
| `priority` | 分支优先级，数值越大越优先 |
| `when` | 边条件 |
| `meta` | 边元数据 |

### 3.4 图字段

| 字段 | 说明 |
|---|---|
| `id` | 图 id |
| `title` | 图标题 |
| `driver` | 驱动器名 |
| `version` | 图版本，建议新图固定为 `2` |
| `entry` | 显式入口节点 id |
| `meta` | 图级元数据 |

## 4. Java API 建议

### 4.1 定义层

建议把当前 `GraphSpec` 继续保留为旧图/兼容入口，但新增一套独立的新图 API。

新图命名采用 `GraphBlueprint`。

### 4.2 编译层

建议增加一个专门的编译对象：

- `GraphCodec`：负责 JSON/对象互转
- `GraphCompiler`：负责校验、补全和拓扑编译
- `CompiledGraph`：只读运行图

其中：

- `GraphCodec` 处理格式。
- `GraphCompiler` 处理规则。
- `CompiledGraph` 处理运行。

### 4.3 运行层

运行层建议继续保持现有职责：

- `FlowEngine`：入口和注册
- `FlowContext`：单次执行上下文
- `FlowExchanger`：单次执行交换器
- `FlowDriver`：具体驱动器实现

## 5. 编译流程

建议新图进入引擎前先走一次编译：

1. 解析 JSON 或 builder 输出。
2. 校验 `id`、`entry`、节点唯一性、边引用完整性。
3. 展开节点和边，建立只读索引。
4. 推导入口、出边顺序、分支优先级。
5. 生成可执行的只读图对象。

这样运行时只做图遍历，不再做结构补偿。

## 6. 兼容策略

旧图和新图应该并行存在，但职责分开。v2 先承担统一运行入口，再逐步成为新图默认入口。

### 6.1 旧图

旧图保留以下兼容点：

- `layout` / `nodes`
- `when` / `condition`
- `link` 单值/数组/对象混合
- 入口推断

这些逻辑都应该放在兼容 codec 里。

### 6.2 新图

新图只认 canonical schema：

- `version = 2`
- `entry` 显式存在
- `nodes` / `links` 结构化表达
- 条件、优先级、元数据字段固定

### 6.3 兼容边界

新图不要再加入更多历史别名。  
一旦把别名继续塞进主格式，后面的结构优化会重新变复杂。

### 6.4 v2 过渡模式

v2 的目标是“一套运行时，两种输入”：

1. 旧应用继续用旧图配置运行，但由 v2 引擎承接执行。
2. 新应用直接使用 `GraphBlueprint`，同样由 v2 引擎承接执行。
3. 迁移完成后，旧图兼容分支可以从编译/解析入口里移除。

也就是说，v2 不是临时副本，而是正式的过渡承载层。

## 7. 与现有实现的关系

当前代码里，下面这些类更适合作为迁移阶段的过渡实现，而不是新图的最终形态：

- `GraphSpec`
- `NodeSpec`
- `LinkSpec`
- `FlowContextImpl`
- `FlowEventBus`
- `FlowExchanger`

它们现在承担了构建、兼容、执行的混合职责。  
新图设计的方向，是把这些职责逐步拆成：

- 规格层
- 编译层
- 运行层
- 兼容层

## 8. 推荐落地顺序

1. 先抽出 `GraphCodec`，把旧图解析从 `GraphSpec` 里移走。
2. 再引入 `GraphBlueprint`，只表达新图。
3. 然后加 `GraphCompiler`，把入口校验和拓扑检查集中起来。
4. 最后把引擎入口改成接收编译后的只读图。

这样改动是递进式的，不会一次性打散现有 API。

## 9. 结论

新图的核心不是“更强的表达力”，而是“更清晰的边界”。

如果要一句话概括：

- 旧图负责兼容存量。
- 新图负责成为未来默认。
- 兼容逻辑负责过渡。
- 运行逻辑只处理执行。
